# OpenChain implementation and continuous-improvement review — 18 November 2026

Initial gaps included no public LaunchStack SECURITY.md, no explicit license inquiry route, floating GitHub Action major tags, no independent recurring CLI/template advisory jobs, no immutable 69-question evidence register, no source-tarball archive, no release component notice register, no explicit generated-project MIT license/third-party notice, and no committee-ready release evidence bundle.

Corrective actions implemented for 3.0.7:

- Added and externally verified the monitored williams@zivoralabs.xyz contact route.
- Added SECURITY.md and active license/security/contribution procedures plus programme participant and competence records.
- Pinned checkout, setup-node and CodeQL actions to immutable commit SHAs.
- Added recurring dependency monitoring as independent matrix targets so one failing audit cannot skip the other.
- Added scripts/openchain-evidence.cjs with fail-closed component metadata validation and exact integrity-verified registry source archiving.
- Added production dependency audits at low severity for both CLI and generated API template to the release gate.
- Added versioned component records, third-party notices, explicit generated-template MIT licensing and release evidence packaging.
- Added guarded 3.0.7 release automation that accepts only the exact default-branch commit, reruns full checks, archives sources/SBOMs/audits/package hashes and publishes its GitHub source release and evidence only after all gates pass; npm publication remains separately and manually authorized.

The programme now treats missing license metadata, non-registry production sources, missing integrity, failed advisory checks, missing template coverage, stale notice files or source archive integrity mismatches as release failures rather than clean results.

- Added deterministic Markdown notice serialization so the committed compliance notices and regenerated release evidence are byte-consistent after formatting.
- Added the exact-commit 3.0.7 release workflow and extended the normal publish workflow so a release evidence archive is generated and attached before a supplied-release self-certification claim is effective.

- On the 2026-11-18 guarded-release run `44388547880`, root qualification and the component archive succeeded, but the generated-template CycloneDX command failed on the literal unrendered `{{PROJECT_NAME}}` package identity. The proposed corrective control generates the template SBOM from a temporary manifest/lockfile copy with only root package names normalized, retains the original shipped template unchanged, and rejects mismatched manifests; release qualification must prove this in the next run. This is not retrospective evidence of a successful publication.

- For GitHub-only 3.0.7 delivery, the release workflow was separated from npm publishing: only the `release/github-only-3.0.7` branch can trigger tag/release creation, and the workflow no longer accepts or uses npm publication credentials. The `publish.yml` workflow remains manual and opt-in. This change does **not** grant an OpenChain self-certification on its own.

- **Observed outcome:** GitHub-only release run [44401159846](https://github.com/wbizmo/launchstack-cli/actions/runs/44401159846) passed and published `v3.0.7` from `7633e826a9b870fdf2cd54f0aa4ba9c82dc9d034` with the exact evidence archive attached. No npm publication was executed. This is technical release evidence, **not** an assertion that outstanding organizational self-certification or OpenSSF Gold requirements are complete.
