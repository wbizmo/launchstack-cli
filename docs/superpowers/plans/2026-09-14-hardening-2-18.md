# LaunchStack 2.1.0 Hardening Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Resolve LaunchStack issues #2–#18, ship the fixes as v2.1.0, and add a verified npm publishing workflow using `LAUNCHSTACK_NPM_TOKEN`.

**Architecture:** Keep the CLI core small while moving security-sensitive operations into focused helpers. Harden the generated Fastify template at the database/config/plugin boundaries, make generation transactional, and make release verification operate on the packed npm artifact rather than source alone. Deployment commands will stop claiming remote success until a provider confirms it.

**Tech Stack:** TypeScript, Node.js 20+, Commander, Zod, Vitest, Fastify 5, Prisma/PostgreSQL, GitHub Actions, npm.

**Spec:** GitHub issues #2–#18 in `wbizmo/launchstack-cli`.

## Global Constraints

- Do not modify `main` directly; work on `hardening/2-18-release`.
- Use `secrets.LAUNCHSTACK_NPM_TOKEN` only as `NODE_AUTH_TOKEN` in the npm publish step.
- Run targeted tests during implementation and one full release gate before merge.
- A green build alone is not sufficient; lint, tests, pack smoke, generated-project checks, and dependency audit must gate release.
- Do not report a deployment as successful unless a remote provider confirms it.
- Preserve backward compatibility where practical; document intentional CLI behavior changes in v2.1.0 release notes.

---

### Task 1: Secure CLI state and generator behavior

**Files:** `src/commands/secrets.ts`, `src/secrets-store.ts`, `src/history.ts`, `src/generator/files.ts`, `src/generator/generate.ts`, `src/generator/template.ts`, `src/git.ts`, `src/commands/docker.ts`, tests under `tests/`.

- [ ] Add tests for secret-key validation, malformed stores, atomic writes, permissions, transactional generation, rename collisions, single-pass rendering, binary-file handling, and Git metadata fallbacks.
- [ ] Replace positional secret values with hidden prompt/`--stdin`; never echo values.
- [ ] Write secret/history state atomically and use restrictive secret permissions where supported.
- [ ] Generate projects into staging directories and commit only after render succeeds.
- [ ] Render only recognized text files and substitute placeholders with one token scan.
- [ ] Collapse Git metadata collection to at most two `execFileSync` calls.
- [ ] Make `docker init` use the same hardened multi-stage/non-root baseline as generated APIs.

### Task 2: Harden generated authentication and configuration

**Files:** generated template env/config/plugins/auth repository/service/routes/schemas, template package manifest, template tests.

- [ ] Add failing template assertions/integration fixtures for refresh-token single-use rotation, duplicate registration races, CORS production defaults, JWT duration validation, auth input bounds, and rate limiting.
- [ ] Consume refresh tokens with a conditional database update inside the same transaction that creates the successor token.
- [ ] Map Prisma unique-email races to HTTP 409.
- [ ] Validate JWT expiries at startup and expose normalized milliseconds for persistence.
- [ ] Require explicit production CORS allowlists unless an unsafe wildcard opt-in is set.
- [ ] Register Fastify rate limiting and apply auth-route limits; bound email/password/token lengths.
- [ ] Upgrade Swagger UI/static dependency line and commit a deterministic generated-template lockfile.

### Task 3: Correct deployment/provider semantics

**Files:** `src/providers.ts`, `src/config.ts`, `src/commands/provider.ts`, `src/commands/deploy.ts`, `src/history.ts`, README/docs/tests.

- [ ] Define one provider registry shared by config validation, help, docs, and templates.
- [ ] Include Fly.io consistently and remove unsupported-provider drift.
- [ ] Record local-only deploy preparation as `prepared`, not `success`.
- [ ] Validate the output path is a directory inside the project before recording preparation.
- [ ] Document that remote deployment confirmation is provider-adapter work rather than silently claiming success.

### Task 4: Make CI/release artifacts authoritative

**Files:** `package.json`, lockfile, `eslint.config.mjs`, `.github/workflows/ci.yml`, `.github/workflows/publish.yml`, release smoke script/tests.

- [ ] Remove floating `latest` ranges and upgrade vulnerable Vitest to a patched release.
- [ ] Add repository/homepage/bugs metadata and npm provenance publishing.
- [ ] Make `check`/`release:check` include lint, tests, build, pack, and packed-artifact smoke tests.
- [ ] CI must use `npm ci` and run the generated-project quality gate.
- [ ] Publish only version-matching `v*` tags and expose `secrets.LAUNCHSTACK_NPM_TOKEN` to npm as `NODE_AUTH_TOKEN`.
- [ ] Verify the packed CLI version and client credential-forwarding protections from a clean tarball install.

### Task 5: Versioning, generated artifacts, and documentation

**Files:** `src/cli.ts`, `package.json`, template package manifest, `README.md`, `CHANGELOG.md`, `RELEASE_NOTES_2.1.0.md`, release documentation, generated `dist/`.

- [ ] Derive CLI version from package metadata/build injection; never hard-code it in `src/cli.ts`.
- [ ] Bump the release to 2.1.0 and regenerate `dist` from current source.
- [ ] Update README commands, provider list, secret input syntax, release flow, and security behavior.
- [ ] Add v2.1.0 release notes and changelog entries mapping the shipped hardening work.
- [ ] Regenerate lockfiles/dist in CI helper, remove the helper, then run the final release gate.
- [ ] Open the PR, inspect exact-head CI, fix only demonstrated failures, and merge only when green.
